## #81 — `available` while Reconnecting

### matterjs-server at 0bd06f22 (read)

1. Availability is two conditions, not one. `Nodes.ts:127-129`: a state is available when it is `Connected` or `Reconnecting`. `Nodes.ts:135-137`: the node's answer is that cached value **and** the node is not waiting for its first report.
2. Only a restored node waits for a first report: `CCH:949-951` sets the wait when `restored` and the change bus is not yet reporting the peer. A commissioned node is registered with `restored=false` (`CCH:2114`), a stored node with `true` (`CCH:1127`).
3. The bus reports a peer from its first established subscription, latched and never cleared, or from the start when the peer is already Connected when watched (`PeerChangeBus.ts:57-63`, `:113-115`, `:118-129`). Changes applied before the latch are dropped (`PeerChangeBus.ts:171-175`).
4. The wait ends on `reportingStarted` (`CCH:611-617` → `:637-658` → `:661-667`): the cache is rebuilt and, when the state is available, `nodeAvailabilityChanged(true)` is emitted — a `node_updated` (`WSH:613-618`).
5. State changes: `CCH:1039-1058` emits `nodeAvailabilityChanged` only when the availability value flips; Connected -> Reconnecting -> Connected of a node that was available flips nothing and sends nothing.
6. For a node that did not wait (a commissioned one), the first subscription sends `node_updated` through `nodeStructureChanged` when the rebuild produced a new snapshot replacing one clients could have seen (`CCH:654-655`, `WSH:620-622`).
7. `available` on the wire is that value: `CCH:1265`. `get_nodes` filters `only_available` on it (`WSH:1445-1454`); `start_listening` is `get_nodes({})` (`WSH:1220-1224`). `update_node` refuses a node that is not available (`CCH:2765-2769`).
8. Commissioning answers with the node details straight after the commission returns (`WSH:1348-1357`, `:1440-1442`; `CCH:2106-2120`), without waiting for a subscription.

### matter.js 0.18.0 (read)

- `NetworkClient.ts:374-398`: Connected = subscription active and (no peer or a session); else Disconnected when disabled or should-be-offline; else WaitingForDeviceDiscovery on the likely-offline latch or a peer without any address; else Reconnecting. (The issue cites `:376-399`; the function is `:374-398`.)
- `NetworkClient.ts:108`: the state is recomputed at the end of `startup()`, so a started node without an active subscription is Reconnecting.
- `ClientNodeLifecycle.ts:49`: the initial state is Disconnected.
- Unverified: that `peers.commission` returns only after the node's `startup()` finished. Seen as grep lines only: `CommissioningClient.ts:348` (`isNewlyCommissioned = true`), `:361` (`await node.start()`). If startup were not finished the state would be Disconnected and matterjs-server would answer `available:false`; the issue's "Reconnecting, so `true`" is therefore the expected case, not a traced one.

### go-fabric v0.28.0 (read)

- `controller/client/network.go:664-676` (`connectionStateFor`) is the same four-way decision; `:626-637` feeds it. `config.go:189-200`: the same four states and values.
- `controller/client/fabricops.go:277`: commissioning starts the node before it returns; `node.go:480-481` recomputes after a start. So at the commissioning answer the node is Reconnecting or already Connected.
- Unverified: the paths that set and clear the likely-offline latch (only the decision function was read on both sides).

### go-fabric-server at origin/main (read)

- `controllerapi/cache.go:80`: `available` is `ConnectionState() == client.Connected`.
- `cache.go:92-94`: `primed` is latched the first time the node is available; `:83-84` carries it over.
- `cache.go:394-416`: `attribute_updated` only when the previous entry was primed (`:395`); `node_updated` when availability, endpoints or the key set changed, or when `primed` flipped (`:413`).
- `cache.go:254`: `only_available` filters on the same value.
- `api.go:253-257`: Start builds the cache from `Registry().Commissioned()` with `snapshot(n, nil)` — the restored nodes; `cache.go:385-391`: a node new to the cache later is announced with `node_added` — the commissioned ones.
- `docs/protocol.md:188-189` states "`available` (the node's connection state is Connected)" as if it were matterjs-server's rule; `:220-222` states the first-report rule.
- `controllerapi/harness_test.go:211-231`: the test harness polls `get_node` until `available` and uses that as "the subscription is up, `attribute_updated` flows from now".

### Difference

| Case | matterjs-server | go-fabric-server today |
| --- | --- | --- |
| Commissioned node, subscription not up yet (Reconnecting) | `available: true` | `false` |
| Node that was Connected, drops to Reconnecting | stays `true`, no event | `false`, `node_updated`; `true` + `node_updated` again on Connected |
| Restored node after a start, Reconnecting, no report yet | `false` until the first subscription | `false` (same) |
| WaitingForDeviceDiscovery, Disconnected | `false` | `false` (same) |

The second row is the larger one for a client: every brief re-subscription flaps the node to unavailable here and not there (`CCH:1042-1044` names exactly this as the reason).

### Verdict: align

Not a deliberate divergence; nothing in go-fabric prevents it. Rule to implement, in matterjs-server's terms:

    available = (state is Connected or Reconnecting) and not (restored and not primed)
    primed    = the node was Connected once since the server started

- `primed` moves from "was available" (`cache.go:92-94`) to "was Connected": it is the bus's reporting latch (item 3) and stays the gate for `attribute_updated` (`cache.go:395`) and the trigger of the one `node_updated` at `cache.go:413` (items 4 and 6).
- `restored` is new on `nodeState`: true for an entry built in Start (`api.go:253-257`), false for an entry first created in `refresh` (`cache.go:385`), carried over from `prev` like `primed`.
- Approximation, stated: matterjs-server latches on the subscription becoming active; go-fabric's Connected additionally needs a session (`network.go:668`). No separate hook was looked for.

### Change for the implementer (after the v0.28.0 / v0.16.0 bump)

Files: `controllerapi/cache.go` (`nodeState`, `snapshot`, the comment at `:23-26`/`:38-41`), `controllerapi/api.go:253-257` (mark the Start entries restored), `docs/protocol.md:188-189` and `:220-222`, `controllerapi/harness_test.go:211-231`, `changelog.md`.

1. A pure function for the rule (state, restored, primed) so it is table-tested; `snapshot` sets `primed` on Connected and `available` from the function.
2. `refresh` (`cache.go:394-416`) needs no new branch: Reconnecting -> Connected of a commissioned node flips `primed` and sends the `node_updated`; a restored node's first Connected flips both.
3. The harness: `available` no longer means "primed". `waitAvailable` must wait for something that does (for example the `node_updated` that follows the first Connected, or a test-only accessor of `primed`); otherwise tests waiting for `attribute_updated` become flaky again (#78).
4. `docs/protocol.md:188-189`: the rule above with `Nodes.ts:122-137`. `:220-222`: after a commissioning the node can already be available in the answer; the first report's values still arrive in a `node_updated`.
5. Record in `docs/protocol.md` (differences that stay):
   - The low item of the issue: a change that lands in the same refresh pass as the first Connected goes out in `node_updated` only (`cache.go:395` diffs against the entry before the pass), where matterjs-server forwards every change after the latch as `attribute_updated` (`PeerChangeBus.ts:118-129`, `:171-175`). No value is lost: `node_updated` carries all attributes (`cache.go:162`). Record, do not align.
   - The topology graph's `available` stays Connected-only: go-fabric `controller/topology/image.go:68`. matterjs-server's topology reads `node.available` (`NetworkTopologyService.ts:221`, `:328`); where that `node` comes from was not traced (unverified), so whether this is a real difference is open — a question for the report, and a go-fabric matter if it is one.
6. Unverified, to check while implementing: whether go-fabric-server's `update_node` gates on availability as `CCH:2768` does (`.available` is read only in `cache.go` at origin/main, by grep).

Tests to add (controllerapi):
- table test of the rule: 4 states x restored x primed;
- a restored node that is Reconnecting at Start is listed `available:false`, absent from `get_nodes{only_available:true}`, and gets one `node_updated` with `available:true` on Connected;
- a commissioned node: the commissioning answer and `node_added` carry `available:true` when the state is Connected or Reconnecting; no `attribute_updated` before the first Connected; one `node_updated` when it comes;
- Connected -> Reconnecting -> Connected of a primed node: no `node_updated`, `available` stays true;
- Reconnecting -> WaitingForDeviceDiscovery: `node_updated` with `available:false`.

## #75 — nodes that failed to load

### matterjs-server at 0bd06f22 with matter.js 0.18.0 (read)

- matter.js keeps a peer that cannot load in `peers` (`Peers.ts:144-161` at v0.18.0: created, error claimed and logged "is unavailable because it failed to load", added) but out of `peers.commissioned` (`Peers.ts:411-413`: `lifecycle.isCommissioned`, false at construction, `NodeLifecycle.ts:23`; asserted by `PeersLoadFailureTest.ts:115`, `:125` at v0.18.0).
- matterjs-server registers only `peers.commissioned` at start (`CCH:1115-1132`); a registration that throws is logged and skipped (`CCH:1129-1131`).
- So such a node is not in its node set: not in `get_nodes` / `start_listening` (`WSH:1449`, `:1220-1224`; `CCH:1167-1169`), not in `node_count` (`WSH:319-323`), `get_node` answers NodeNotExists (`WSH:1469-1471`), and `remove_node` answers NodeNotExists (`WSH:2155-2159` -> `CCH:1189-1190` -> `:2308-2311`).
- No command removes it. Negative by grep only: `failed to load|construction.(error|status)|LoadFail` over `packages/ws-controller/src` and `packages/matter-server/src` at the pin hits nothing but the BLE import (`MatterController.ts:71`).

Answer to the issue's question: matterjs-server does **not** list such nodes as unavailable; it does not know them.

### go-fabric v0.28.0 (read)

- A node that failed to load stays in the registry (`controller/client/registry.go:319-330`), is not commissioned (`record.go:751-754`; `registry.go:692-700` leaves it out of `Commissioned()`), but answers `PeerAddress` from its stored record (`record.go:726-737`) and is found by `GetByAddress` (`registry.go:729-736`).
- `Registry.Decommission` refuses it with its load error before anything runs (`fabricops.go:98-112`, doc `:291-293`); `Registry.Forget` drops it locally — node closed, rows erased, protocol peer deleted (`registry.go:508-514`, `:522-560`).

### go-fabric-server at origin/main (read)

- Hidden everywhere on `/ws`: `cache.go:69`, `:372`; `api.go:253`; `cmd_node.go:36` answers NodeNotExists, so `remove_node` (`cmd_node.go:85-99`) never reaches `Decommission`.
- This equals matterjs-server's behaviour in every command read above.

### go-fabric-ui v0.16.0 (read, for the cut)

- The controller pages show the failure: `load_error` on the diagnostics peer (`contract/openapi.yaml:3165`, `fabricui/gofabric/diagnostics.go:46`).
- They cannot remove it either: `fabricui/gofabric/gofabric.go:647-660` calls `Registry.Decommission` only; no call of `Registry.Forget` under `fabricui/gofabric` (grep).

### Verdict

1. **Listing: already aligned, keep hidden.** There is no difference from matterjs-server to record. Listing such nodes as unavailable would be going ahead of matterjs-server, with a node no client can interview; how clients treat that was not read (unverified), and nothing in the reference supports it. `docs/protocol.md` gets one sentence stating the behaviour (a stored node that failed to load is not a node on `/ws`, as matterjs-server registers only `peers.commissioned`, `CCH:1115`).
2. **Removal: the gap is real, and going ahead is the only way to close it on `/ws`.** Judgement, for the owner to confirm: `remove_node` for a node id whose only match is a load-failed node drops it with `Registry.Forget` and answers `null`; matterjs-server answers NodeNotExists there (`CCH:2309-2311`). It is the same kind of removal matterjs-server already does for an unreachable node — local, the device keeps the fabric (`CCH:2329-2334`). Recorded in `docs/protocol.md` as going ahead (go-fabric-server `CLAUDE.md:61-62`).
3. **Open question on the cut:** an operator learns of such a node from the controller pages, not from `/ws` (it is not listed there), and the pages cannot remove it. Whether removal belongs in go-fabric-ui (a contract decision there) in addition to, or instead of, `remove_node` is the owner's call; it is not part of the bump.

### Change for the implementer (if 2 is confirmed)

Files: `controllerapi/cmd_node.go` (`cmdRemoveNode`, `:85-99`; `s.node` at `:29-40` stays as it is for every other command), `docs/protocol.md` (command table `:109`, the node-data section), `changelog.md`.

- In `cmdRemoveNode` only: look the node up by address; when it exists, is not commissioned and `LoadError()` is non-nil, call `Registry().Forget` and answer `null`; a Forget error goes through `nodeError` (the node stays in the registry and a second call retries, `registry.go:512-513`).
- No event: the node was never in the cache, and `refresh` returns for it (`cache.go:376-377`). Do not add a `node_removed`.
- Every other command keeps answering NodeNotExists for such a node.

Tests to add:
- `get_nodes`, `start_listening`, `get_node` and the server info's node count leave a load-failed node out (pins today's behaviour);
- `remove_node` on it: answer `null`, the registry no longer holds it, no `node_removed` on a listening connection; a second `remove_node` answers NodeNotExists;
- `remove_node` on an unknown id still answers NodeNotExists;
- another command (for example `interview_node`) on the load-failed node answers NodeNotExists.
- Unverified: no helper that produces a load-failed node exists in go-fabric-server's tests (grep for `LoadError|ErrLoadFailed` at origin/main hits no test); how go-fabric's own tests produce one was not read.
