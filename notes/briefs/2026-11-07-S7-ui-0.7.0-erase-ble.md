## 2 Erase a device node (#50; owner decisions 2026-11-07)

**Decision (owner):** Erase = `node.FactoryReset`, then the node served
again on the erased store; the source the pages read follows the new node;
the UI's port stays error-only; the page recovers by polling (go-fabric-ui
`changelog.md` 0.7.0 "polls the status until the node answers again";
`ui/src/lib/pages/node/Fabrics.svelte:8, :89-100` at v0.7.0).

What go-fabric gives: `node.FactoryReset` removes every fabric (each
controller's Leave), stops the node and erases the credential store and
the endpoint records; a Go node is single-use, so the host builds a new
node on the same store and starts it, "exactly as after a restart"
(`node/factory_reset.go:20-45` at v0.18.0; the pattern
`fabrictest/device.go:396-416`, `Device.FactoryReset`: reset, drain,
`startLocked`). The new node starts uncommissioned with a fresh UniqueID.

What go-fabric-ui expects: the handler keeps the `NodeSource` it was given,
so a host that builds a new node hands over a source that delegates to the
current node (`fabricui/options.go:231-244`, `Options.Erase`;
`docs/embedding.md:111-128`). From 0.7.1 that source is go-fabric-ui's
**`fabricui.NodeSwitch`** (wave U8; owner, 2026-11-08, Decided 1):
`NewNodeSwitch(initial NodeSource) *NodeSwitch`, `Set(NodeSource)`,
`Current() NodeSource`; every `NodeSource` method delegates to the current
target; a running SSE stream keeps the old target until the page
reconnects. The host writes no delegator. (For a registry node a new
`Source` value in `Registry.List` would also do — `managedHandler`
rebuilds the sibling when `sameEntry` sees another `Source`,
`fabricui/registry.go:110-124, :166-178` — and is not used, §2.1.)
`Status.erase` reports whether the host wired it (`handlers_node.go:67-69,
:135`); the route is `POST /node/maintenance/erase` and
`/nodes/{key}/maintenance/erase`, admin, body `{"confirm":"erase-node"}`,
501 without an `Erase` (`handlers_node.go:343-380`).

### 2.1 Shape — one `NodeSwitch` for every node

- `bridgeHalf` (`internal/daemon/nodes.go:94-100`) becomes the unit that
  outlives its node: `spec`, a mutex serialising its lifecycle, the
  current pair `{node *node.Node, srv *bridgeapi.Server}` behind an
  `atomic.Pointer`, `sw *fabricui.NodeSwitch` created once at the first
  start with `fabricui.NewNodeSwitch(node)`, and `restartErr` (the last
  failed restart, with its time; nil while the node runs). The pages get
  the switch: `o.Node = def.sw` (`web.go:39`) and `ne.Source = h.sw`
  (`registry.go:202`), never a bare `*node.Node`; the half implements no
  `NodeSource` method of its own.
- One shape for the default node and the registry's — the standard's "one
  shape, no convenience seam". The alternative (default node through the
  switch, registry node through `publish()` with the new `*node.Node` as
  `Source`, as #50's text suggests) is two mechanisms for one action and
  is rejected here; it stays documented as go-fabric-ui's other path.
- The deferred stop of the default node (`run.go:317`) and the registry's
  `stopAll` (`registry.go:179-188`) stop the half's *current* node, so a
  node brought back by an erase is the one the shutdown stops.
- `bridgeRoutes` gains `replace(key, srv)` in place (the index of
  `default` stays 0, which `get("")` relies on, `nodes.go:127-137`);
  `muxRoutes` already resolves the half per request (`http.go:59-71`), so
  nothing else moves.
- **Arch:** nothing moves. The server implements no `NodeSource`, so
  `clock.Clock` (a return type of `NodeSource.Clock()`, `options.go` at
  v0.7.0) is never named in `internal/daemon`; `clock` stays `testOnly`
  in `internal/arch/arch_test.go:83`.
- `expvar` names: `startBridge` publishes under
  `bridgeMetricsPrefix(key)` (`run.go:429`); a second `New` with the same
  prefix shares the variables and does not panic
  (go-fabric `node/metrics/expvar/expvar.go:34-45` at v0.18.0), so the
  counters of the new node continue the old node's. Acceptable; say so in
  `docs/operations.md`.

### 2.2 Sequence — `erase(ctx, h)` in one place

A `nodeLifecycle` value (the daemon's context, `startFunc`, routes,
logger — what `registryOptions` carries today, `registry.go:82-90`) owns
start and erase for both the default half and the registry's; the registry
embeds it. The erase, under the half's mutex:

1. `ctx` as `Delete` bounds it: `context.WithTimeout(context.WithoutCancel(ctx), 30*time.Second)`
   (`registry.go:291-293`) — a page that goes away does not leave a node
   half erased.
2. `cur.srv.Shutdown(ctx)`: the bridge client gets `server_shutdown`
   (`bridgeapi/api.go:176-199`); the route stays, so a client that dials
   back meanwhile is refused by the closing server and retries.
3. `cur.node.FactoryReset(ctx)`; an error is logged
   `fabricserver.node.erase_failed` and returned — nothing is restarted on a
   failed erase, the half keeps the stopped node (Stop is idempotent,
   `node/node.go:912-920`).
4. `startFunc(lifecycle ctx, h.spec)` — the daemon's context, as `Create`
   does (`registry.go:239-241`): a fresh `bridgeapi.Server` (one cannot be
   started twice, `bridgeapi/api.go:129-136`) and a new node on the erased
   store, same key, port, discriminator, passcode and label. **A start
   error keeps the daemon up** (owner, 2026-11-08, Decided 2; the same
   rule holds in go-ha2fabric): it is logged
   `fabricserver.node.restart_failed` with `node=<key>` and returned (the
   route answers it through `serverError`, `handlers_node.go:373-376`);
   `sw` is not `Set`, so the switch keeps the stopped node as its target
   (what that node's status then reports is go-fabric's answer for a
   stopped node — not read; the warning below is the operator's signal);
   the half records `restartErr`, and the daemon's `Warnings` (§2.3)
   surfaces it on every status page as `{code: "node_restart_failed",
   message: "<key>: <err>", since}` — the surface go-fabric-ui gives a host
   for its own findings (`fabricui/options.go:268-285` at v0.7.0;
   `Status.warnings`, `handlers_node.go:70-72, :150-155`; the sibling
   handlers share it, `handler.go:389-401`). **Retry:** Erase again —
   `FactoryReset` on the stopped node erases an already erased store
   again (`node/factory_reset.go:27-28`) and step 4 runs anew; a restart
   of the daemon also brings the node back (the store is erased). No
   `os.Exit` on this path.
5. `routes.replace(key, srv)`, `cur.Store(new)`, `sw.Set(new.node)`,
   `restartErr` cleared; for a registry node `publish()` (the `Source`
   value — the switch — is unchanged, so the pages' handler and its cache
   stay, `registry.go:166-178`). Log `fabricserver.node.erased` with
   `node=<key>`.

The registry's `Delete` keeps its own path (`registry.go:283-322`): it
ends the node for good, no restart. Both call `FactoryReset` through the
half, so the half is the only place a node's lifecycle is driven.

### 2.3 Wiring

- `webHandler` (`web.go:33-44`): `o.Erase = lifecycle.eraser(def)` when
  `def != nil`; `o.Warnings = lifecycle.warnings` — one `Warning` per
  half (default and registry) whose `restartErr` is set, `Since` the
  failure's time. The server wires no `Warnings` today (no `Warning` in
  `internal/daemon/*.go`); `NodeEntry` has no per-node field
  (`options.go:97-130`) and the sibling handlers answer the host's
  (`handler.go:389-401`), so the one function names the node in
  `Message`.
- `publish()` (`registry.go:196-207`): `ne.Erase = r.eraser(h)` for a
  running half; a half that failed to start (`startAll`,
  `registry.go:162-176`) is listed with `Source` nil and no `Erase`, as
  today.
- `Options.Erase`/`NodeEntry.Erase` need admin (go-fabric-ui's route is
  admin); `Options.Admin` stays the flags' rule (`web.go:83-99`).

### 2.4 Is it the best architecture

- Better than before: deleting was the only way to get a clean node; now
  the same key, port and codes come back without a restart, and the bridge
  client reconnects to the same path.
- Better than the comparison target: matter.js's `ServerNode.erase` comes
  back online in place (`node/factory_reset.go:40-45` cites
  `ServerNode.ts:159-200`); this host does the same, at the same route the
  pages use for every node.
- The right cut: `FactoryReset` is go-fabric's; the route, confirmation,
  polling and the `NodeSwitch` — the source that follows a replaced node,
  which every erasing host needs (go-ha2fabric's follow-up said the same,
  go-fabric-ui `docs/reports/U7.md:193-203`) — are go-fabric-ui's; the
  lifecycle (a new node on the store, a new bridge half, the route, the
  `Set`, the warning) is the daemon's and lives in one type. The host
  writes no delegator (Decided 1).

## 3 Why a pairing has no BLE (#48, the server's part)

### 3.1 The defect, settled from the code

- **The pairing in #48 was the UI path**, not `/ws`: "started in the
  controller pages" is `POST /api/v1/controller/commission` →
  go-fabric-ui `source.Pair`, and the owner confirmed on the installation
  that the same pairing with the Thread credential picked in the page's
  select paired over BLE (#48, owner's second comment; go-fabric-ui#49's
  comment). `source.Pair` sets `opts.BLE` only when the request names a
  credential (`fabricui/gofabric/gofabric.go:273-277` at v0.7.0;
  `networkOf` returns nothing for an empty selection, `:229-231`); the page
  names none unless picked (`Commission.svelte:30, :49-52, :54-63`). That is
  go-fabric-ui#49, open at v0.7.0 (its 0.7.0 changelog has no BLE
  entry; the lines above are unchanged) and fixed by wave U8 in 0.7.1,
  which §1 bumps to. **Out of scope here**: the server only aligns its
  reason names with U8's (§3.2).
- **`/ws` `commission_with_code` is right:** without ids it falls back to
  the `default` entries (`cmd_commission.go:76-85, :128`;
  `settings.go:145-181`; `credentialID`, `cmd_server.go:195-200`) and hands
  `PairOptions.BLE` to go-fabric when a central exists, `network_only` is
  off, the code allows BLE and a Wi-Fi or Thread network results
  (`cmd_commission.go:133-135`). Not handed over when: no central
  (`Options.BLE` nil, `api.go:81-83`); `network_only`; a QR code without
  bit 1 (`capabilityBLE`, `:254-257`); no id named and no `default` entry
  stored, or an entry with an empty SSID / undecodable dataset
  (`:85-93`). Home Assistant's `matter/set_thread` stores without an id,
  i.e. as `default` (#48, owner's comment), so HA's flow gets BLE.
- **The central's hand-over is right:** `bleCentral` → `controllerOptions`
  → `Options.BLE` (`run.go:230-233, :250, :568-581, :606-611`;
  `TestBluetoothProxyWired` asserts it, `proxy_test.go:91`); the pages'
  template is `api.PairOptions()` with the same central
  (`controllerui.go:33`, `host.go:162-168`), so `capabilities.ble` =
  "a central exists" (go-fabric-ui `gofabric.go:162-164`) is correct and
  stays: it describes the host, not one request.
- **go-fabric is right:** `Pair` builds the BLE scanner only from
  `PairOptions.BLE` (`controller/pair_race.go:49-53`) and refuses BLE
  without a network as `ErrConfiguration` (`controller/controller.go:674-676`),
  which neither path can reach (both set BLE only with a network).
  `ble_not_enabled` is logged for a QR code naming BLE when no BLE
  transport was installed (`client/discovery/session.go:409-411`): the 15:43
  attempt was a QR code without a credential — the line was correct, and
  the manual code at 15:50 carries no capabilities, so it could not appear.
  `proxy_taken` fires in `subscribe()` once `StartScanning` runs
  (`ble/esphome/central.go:271-296`, `proxy.go:396-412` at v0.13.10) — it
  was absent because no scanner existed, not because of the proxy. No
  hand-over to go-fabric.
- **The server's own defect is the missing statement:** neither path says
  why BLE was or was not part of a pairing (`cmd_commission.go:106-143` has
  no log call). The server fixes its path; go-fabric-ui#49 fixes the
  pages'.

### 3.2 The fix — one decision function, two log lines

- Factor the condition of `cmd_commission.go:133` into a pure
  `bleChoice(central bool, pc controller.PairingCode, networkOnly bool, wifi *commissioner.WiFiNetwork, thread *commissioner.ThreadNetwork) (use bool, reason string)`
  in `cmd_commission.go`; reasons (in this order, the first that holds):
  `no_central`, `network_only`, `code_without_ble`, `no_network` — the
  names and precedence of go-fabric-ui#49/U8 (Decided 3); `""` when BLE is
  used. The rule does not change
  (`docs/by_design.md` B20, `:110-117`, holds as written).
- Log, at `cmd_commission.go:133` after the choice, on `s.log` in the
  `fabricserver.*` style (`cmd_server.go:245-249`):
  - `fabricserver.commission.ble` Info when used: `network=wifi|thread|wifi+thread`,
    `wifi_id`/`thread_id` as named by the request or `default` — ids only,
    never the SSID or the dataset (`TestSecretsNotLogged`, `s3_test.go:276-300`).
  - `fabricserver.commission.ble_skipped` Info with `reason` when a central
    exists and BLE is not used — the operator configured BLE and should
    see why it was left out; `reason=no_network` is the
    actionable one and gets a `hint` ("store a credential with
    set_wifi_credentials/set_thread_dataset without an id, or name one").
    Without a central no line: `server_info.bluetooth_enabled` already says
    BLE is off (`events.go:104`), and matterjs-server logs nothing either.
- The pages' path logs nothing here: it is go-fabric-ui's `source.Pair`.
  When #49 lands with a default fallback, the server's `Credentials` port
  already answers `""` as the default entry (`host.go:126-141`,
  `controllerui.go:87-91`) — nothing to add in that bump.
- `docs/protocol.md:83` still says "over BLE with `--bluetooth-adapter`";
  fix to "with `--bluetooth-adapter` or `--bluetooth-proxy`" (stale since
  S5). Not a `/ws` shape change: no `make compat-python`.

### 3.3 Is it the best architecture

- One predicate, tested as a function, logged once; no second rule beside
  go-fabric-ui's (whose copy, `gofabric.go:259-263`, cites this file).
- Forward-looking: go-fabric-ui 0.7.1 (U8) adds the pages' statement, so
  both paths say the same thing with the same four reason names
  (Decided 3).
- The right cut: go-fabric says what it discovered on (`discovery.initiating`
  with `note="BLE not requested"`, `session.go:391-404`); the host says what
  it handed over and why — the one thing go-fabric cannot know.
