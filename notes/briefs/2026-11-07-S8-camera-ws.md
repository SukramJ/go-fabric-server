## 1 Composition (daemon, `internal/daemon/run.go:254-300`)

- `cfg.Camera = &controller.CameraConfig{}` (`controller/serve.go:47-53`;
  the controller then serves endpoint 1 with the requestor, `:55-62`) and
  `cfg.TCP = controller.TCPConfig{Outgoing: true}` (`controller/tcp.go:20-27`;
  `camera.New` refuses without it, `service.go:25-28`; outgoing TCP is a
  soft hint that falls back to UDP for a peer without TCP,
  `controller/controller.go:177-181`).

  hook chain (`api.Hooks` → `pageHooks.Wrap` → `changes.Install`,
  `run.go:259-275`): `Install` wraps `cfg.HooksFor` and runs the host's
  hooks first (`reports.go:37-39`), as `topology.Changes.Install` does.
- `cam, err := camera.New(ctx, ctrl, camera.Config{Reports: &reports,
  Observer: api.CameraObserver(), Logger: log})` after `controller.New`.
  The observer is the server's before the service exists, as `HooksFor:
  api.Hooks` is (`run.go:259`): `CameraObserver()` returns three closures
  over the `*Server` (§5).
- `api.Start(ctx, ctrl, controllerapi.Services{Topology: topo, Camera: cam})`
  — **decision:** `Start(ctx, b Backend, topo *topology.Service)`
  (`controllerapi/api.go:207`) becomes `Start(ctx, b Backend, svc Services)`;
  a fourth positional parameter would be the convenience seam the standard
  forbids, and the next service (OTA, phase 25) joins the struct. Callers:
  `run.go:293`, `controllerapi/harness_test.go:109` (its `env` gets the
  camera, §8). `backendRef` (`api.go:133-136`) carries both.
- Shutdown order: `api.Shutdown` (sockets closed first, `api.go:266-290`),
  then `cam.Close(ctx)` (`service.go:205-207`; ends every session, which is
  what docs:2305 describes — "every socket is closed before the sessions are
  ended; `server_shutdown` is what a client sees"), then `topo.Close`,
  `pageHooks.Close`, `ctrl.Close` (`run.go:276-290` extended).
- **No flag; camera always on**, as matterjs-server composes its
  `CameraControllerEndpoint` unconditionally (`ControllerNode.ts:147`, as
  cited by go-fabric `controller/serve.go:55-59` and #410). The daemon logs
  the camera endpoint once (`controller.serve.endpoints`, `serve.go:156`,
  already does). `--disable-auto-subscription` leaves the watch without
  reports: only a reissued id ends a session, as `camera_restarted`
  (docs:2290) — one line in `docs/operations.md:27`.
- *Best architecture?* Yes: one identity, no second socket, the same
  composition as matterjs-server, nothing the operator has to switch on
  before Home Assistant's camera entity works. Decided (owner,
  2026-11-08, §12 Q1): always on, no `--camera` flag; the alternative
  `--camera=false` for an operator who wants no outgoing TCP stays on
  record as not taken.

### 3a Wire names

- Codecs are matterjs-server's SDP spellings, not the enum member names:
  video `H264`, `H265` (Hevc), `H266` (Vvc), `AV1`; audio `OPUS`, `AAC`
  (AacLc); image `JPEG`, `HEIC`; an unnamed value as its decimal digits
  both ways; matched case-insensitively (`wireNames.ts:16-31, :44-73`;
  docs:1843-1849). The schema's own names are the matter.js member names
  (`protocol/schema/schema.json:7322-7329`: `Hevc`, `Vvc`, `Av1`), so these
  eight names are a **wire-contract table in `camera_wire.go`, cited
  `wireNames.ts:16-31`** — not Matter knowledge (the ids and enum values
  stay the defs'), and the host's job by #410's comment. go-fabric holds
  the same table unexported (`controller/camera/policy_sdp.go:785-824`,
  `manager_snapshot.go:21`); §10(a) asks for the export so the table exists
  once — the server switches when it lands.
- Stream usages (`Internal`, `Recording`, `Analysis`, `LiveView`) and
  `two_way_talk_support` (`NotSupported`, `HalfDuplex`, `FullDuplex`) are
  the enum member names (`wireNames.ts:41-42` reads them off the enum),
  equal to the defs' constants (`csdef.StreamUsageLiveView`, …): read them
  through `protocol/schema`'s enum names when one lookup reaches them
  (`protocol/schema/model.go:72-81` holds `Enum.Values[].Name`), else the
  same cited table. `camera_start_stream` refuses `Internal` and any other
  name with 8 (docs:1848); go-fabric refuses it too (`service.go:487`).
- `features` are the specification's titles in bit order
  (`Capabilities.Features []string`, go-fabric's; docs:1288-1290).

## 5 Events, ownership, holding (`controllerapi/camera_events.go`)

Per connection (`wsConn`, `conn.go:17-39`): two opt-in flags set in
`handle` before `dispatch` (`dispatch.go:131-154`; handler.ts:820-827
"must run before the command is dispatched"): `webrtc` by
`send_webrtc_provider_command`, `camera_start_stream`,
`camera_provide_answer`, `camera_provide_ice_candidates` (handler.ts:150-157);
`camera` by any of the seven `camera_*` (handler.ts:159-171;
`send_webrtc_provider_command` is schema 12 and does not count, docs:2294).
The connection id (`conn.id`) is the session owner (`StartRequest.Owner`).

- **`webrtc_callback` of an owned session.** `Session.Signals()` is the
  session's own channel, buffered from the camera's first signal and closed
  at the end (`session.go:151-176`, mailbox `:269-335`). The handler returns
  the result and sets `call.after` (`dispatch.go:16-21`, run after
  `conn.reply`, `:151-153`) to start one goroutine per session that drains
  `Signals()` into `webrtc_callback` frames sent with `SendReliable`
  (handler.ts:763-770 "control-plane: never coalesced or dropped";
  `protocol/conn.go:250-253`). So the hold until the response is a property
  of the API, not a re-routing table: the response carrying the id goes out
  before the first event of the session (docs:1408), to the owning
  connection and no other (docs:2255-2259). Frame: `{event_type,
  webrtc_session_id, node_id, endpoint_id, fabric_index, client_session_key?,
  data}` from `Signal.Session` (`wrdef.WebRTCSessionStruct{Id, PeerNodeId,
  PeerEndpointId, FabricIndex}`, `definition_gen.go:47-57`;
  `WebRtcCallbackBridge.ts:55-66, :81-88, :94-107, :114-121`); `data` per
  kind: `offer` `{sdp, ice_servers?[{urls (always a list), username?,
  credential?, caid?}], ice_transport_policy?}` from `Signal.Offer`
  (`wrdef.OfferRequest`, `:204-209`; bridge.ts:16-25, model.ts:365-381),
  `answer` `{sdp}` (narrowed by go-fabric, `service.go:39-41`),
  `ice_candidates` `{ice_candidates[{candidate, sdpMid, sdpMLineIndex}]}`
  (nulls kept, `ICECandidateStruct` `definition_gen.go:178-182`;
  bridge.ts:101-105), `end` `{reason}`. On a failed start nothing is
  drained: the client never learned the id (docs:1408; `startingSessionSignalling.ts:64-66, :113-120`).
- **`webrtc_callback` of an ownerless session** (raw route): `Observer.Signal`
  (`service.go:76-78`) → every `webrtc`-opted-in connection (docs:2261-2269;
  handler.ts:776-793), no key.
- **`camera_session_ended`.** `Observer.SessionEnded(SessionEnd{NodeID,
  Endpoint, SessionID, Cause, Reason, RequestedBy, Owner, Key})`
  (`service.go:106-118`): skip `EndReleased` (handler.ts:717; docs:2299-2305);
  skip the connection whose id is `RequestedBy` (handler.ts:719; docs:2296);
  `Owner != ""` → only the owner's connection; `Owner == ""` → every
  `camera`-opted-in connection (handler.ts:720; docs:2297). Frame `{node_id,
  endpoint_id, webrtc_session_id, cause, reason?, client_session_key?}`
  (handler.ts:721-728; model.ts:836-846); `cause` is `EndCause`'s string
  (`service.go:84-104` spells matterjs-server's five, model.ts:829-834).
  **Held** while the owner's start for that (node, endpoint, key — or id once
  `StartStream` returned) is unanswered; released in order after the
  response, dropped on an error response (handler.ts:741;
  `startingSessionSignalling.ts:79-138`). A `SessionEnd` for an id this
  connection never handed out is dropped (#410 comment: a failed start can
  end).
- **`camera_stream_evicted`.** `Observer.StreamEvicted(StreamEvicted{NodeID,
  Endpoint, Kind, StreamID})` (`manager.go:95-100`) → every `camera`-opted-in
  connection, the requester included (docs:2326; handler.ts:743-760). Frame
  `{node_id, endpoint_id, kind, stream_id}` (model.ts:857-862).
- **ICE candidates by key before the response**: queued on the start
  (≤ 64, else 8 with matterjs-server's wording,
  `startingSessionSignalling.ts:14-15, :165-170`), sent after the held
  events with one `sess.ProvideICECandidates` carrying all queued
  candidates in order (`:106-112, :178-227`; go-fabric splits them per
  message, `session.go:186-258`), each command answered with its own
  outcome; a key whose start failed or whose session ended → 8 (docs:1684).
- **Connection close**: `svc.Release(ctx, conn.id)` in `wsConn.close`
  (`conn.go:93-104`; handler.ts:810-812; `service.go:316-323`), no events
  to the closed connection. Observer callbacks must not block
  (`service.go:69-70`): `SendReliable` queues, the drain goroutines own the
  channels; nothing under `s.mu`.
- *Best architecture?* Yes. matterjs-server routes one shared callback
  stream by a lookup of the owner at emit time (handler.ts:771-797) and
  holds with a side table; here the API hands each session its channel, so
  ownership is the channel and the hold is the drain's start. The one
  table left — held `SessionEnd`s and queued candidates per unanswered
  start — is what #410 named host-side.

## 13 Better than matterjs-server, better than before, the right cut

- **Better than matterjs-server.** Same wire, fewer moving parts: the
  session's signals are a typed channel the owner drains, so the hold and
  the routing need no emit-time owner lookup and no re-routing table
  (handler.ts:771-797 vs §5); the five error payloads are built from typed
  errors with the fields already named (no `"track" in detail` branching,
  types.ts:274-301); the compat fixtures and the python client hold the
  shapes against the reference at every CI run; one static binary with the
  controller's camera role included. Taken over unchanged, because they are
  the contract: the names, the opt-in rules, the three silent endings, the
  64-candidate queue.
- **Better than before.** The server stops lying by omission: a schema-14
  client got a camera entity and a refusal at first use (`dispatch.go:167`);
  now every command of the dispatch is answered or named as waiting for
  go-fabric (OTA, Thread), and the error table has no "defined, not
  raised" camera rows. The controller facade gets its first consumer of
  `controller/camera`; what the server finds missing (§10) goes back as
  facade asks, as S1–S3 did for the client.
- **The right cut.** go-fabric: every Matter rule — allocation, SDP,
  eviction, the session registry, the sweep, the signals over the
  controller's identity, the typed errors. This server: the wire shapes,
  which connection owns a session, what is held until a response, the key,
  the error payload's spelling, the python client's compatibility.
  go-fabric-ui: a later consumer of the same `controller/camera` (not this
  wave). go-ha2fabric: the camera on the other end of the live test. Nothing
  here reaches below the facade (§2), and nothing in go-fabric knows the
  wire (`controller/camera/doc.go:1-68` names the host's part the same way).
