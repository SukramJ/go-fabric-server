## §1 The daemon — `8e41c07`

- **`--bluetooth-proxy host[:port][,key]`**, repeatable: `proxyList`, a
  `flag.Value` that appends one `esphome.ParseProxy` result per use; its
  `String` names addresses only, never a key. `FABRIC_SERVER_BLUETOOTH_PROXY`
  supplies one proxy when the flag is not given.
- **`bleCentral(Config, *slog.Logger)`** picks the backend: proxies give
  `esphome.NewCentral(proxies, esphome.Options{Logger})` (through the
  stubbable `newProxyCentral`); the adapter keeps the BlueZ path (now
  `adapterCentral`); both is a start-up error ("one BLE backend, not
  both"). A refusal is wrapped as `--bluetooth-proxy: <module error>`. The
  daemon logs `fabricserver.ble_proxies` with the addresses;
  `ble.esphome.proxy_taken` comes from the module.
- **Shutdown**: the central closes before the controller (a `sync.OnceFunc`
  deferred again after the controller's close; the early defer covers a
  failed start).
- **`server_info.bluetooth_enabled`** is `s.opts.BLE != nil`, as
  matterjs-server's `ble.enable` (`WebSocketControllerHandler.ts:1182`). It
  was always false before, also with `--bluetooth-adapter`.
  `ble_proxy_enabled` stays false (by_design B22). `capabilities.ble` on the
  pages already followed `PairOptions.BLE`.
- **Errors**: `commissionError` keeps `%v`, so `ErrProxyBusy`,
  `ErrNoActiveConnections` and `ErrInvalidKey` reach `commission_with_code`'s
  details as they are (reason `other`).
- **Arch**: `ble/esphome` in the facade list; test-only
  `ble/esphome/esphometest`, `controller/ble/bletest`, `bridge/bridgetest`,
  `transport/btp` (Q2).
- **Tests**: `internal/daemon/proxy_test.go`:
  - `TestBluetoothProxyFlag`: one proxy, several proxies, a bad spec, the environment variable, and a `String` without the key.
  - `TestBluetoothProxyWired`: the central goes into `Options.BLE`, both backends are refused without opening either, and a refusal names the flag.
  - `TestRunRefusesBothBackends`.
  - `TestCommissionThroughProxy`: an in-process pairing on `fabrictest` through `esphometest` with Noise. `server_info` shows `bluetooth_enabled` true and `ble_proxy_enabled` false, the pages show `capabilities.ble`, Wi-Fi is set over `/ws`, and `commission_with_code` with the manual code runs PASE over BTP through the proxy, provisions Wi-Fi and fires `node_added`.
  - `controllerapi/errors_internal_test.go`: `TestCommissionErrorProxy`.
  - `newPagesEnvWith` widens the pages env with a device configuration and a central.
- Notices: `THIRD-PARTY-NOTICES.md` gets the new direct module plus
  `flynn/noise` and `golang.org/x/crypto` (BSD-3-Clause) with texts in
  `licenses/`. The schema regeneration moves only the `GoFabricVersion`
  stamp.

## Differences from the brief

- `ble/esphome` has no tag at v0.13.5. It is pinned by pseudo-version at
  that commit, as §0 allows. Its `go.mod` still requires go-fabric v0.13.3,
  and the server's v0.13.5 require wins in MVS (Q1).
- `esphome.Options.Clock` is not set: `clock` is a test-only import under
  the arch rule, and nil is the system clock.
- The add-on schema is `- str?` (the Supervisor's list form), not
  `list(str)?`, which is the Supervisor's enum syntax.
- The add-on's options become flags in `script/run.sh` (what
  `addon/Dockerfile` copies as `/run.sh`). There is no `addon/run.sh`.
- `bluetooth_enabled` was false with BlueZ too. It is fixed for both
  backends.
- The in-process pairing needs four test-only imports below the facade (Q2).

## Decisions

- **D1** Both backends is a start-up error, not matterjs-server's
  "warn and prefer" (B22): the two flags name different mechanisms.
- **D2** The environment variable carries one proxy. Several proxies go
  through repeated flags, as the add-on passes them, because the key's
  comma rules out a comma list.

## Left out

The Thread border-router commands (go-fabric wave 26a). The owner's live
test against real proxies is the acceptance.

## Questions

- **Q1** `ble/esphome` has no tag at v0.13.5, and its `go.mod` still
  requires go-fabric v0.13.3. Recommendation: in go-fabric, bump that
  require to v0.13.5 and tag `ble/esphome/v0.13.5` (as `ble/bluez/v0.12.1`
  was tagged), then re-pin here in the next bundle.
- **Q2** fabrictest has no BLE side for a `Device`. The daemon's
  in-process pairing therefore builds the peripheral itself from
  `controller/ble/bletest`, `bridge/bridgetest.ServeConn` and
  `transport/btp`, which are test-only arch exceptions. Recommendation: a
  `fabrictest.Device.BLEPeripheral()` (or `esphometest.ForDevice(dev)`) in
  go-fabric so these exceptions can go.
