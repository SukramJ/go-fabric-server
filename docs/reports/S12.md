  and its advertisement and waits for both (go-fabric `bridge/ble.go`
  `StopBLE`); `ble/bluez`'s `Serve` refuses only a second concurrent call
  (`ErrServing`) and resets its state per call
  (`ble/bluez/peripheral_linux.go` `Serve`); the node does not close the
  peripheral (the example closes it itself). The Wi-Fi driver holds no
  per-node state. So one peripheral and one driver serve every run.
- `internal/arch/arch_test.go`: `wifi/wpasupplicant` in `facade`, with a
  comment; `go.mod` requires it at `v0.22.1` directly. godbus was already
  in through `ble/bluez` at the same version: the dependency set gains
  only the module itself.

## Better than others, better than before, the right cut

- **Better than others.** matterjs-server's server runs a controller and
  has no device-side BLE: its nodes, where it has any, are reached over IP
  only. chip's example apps take BLE and Wi-Fi as build options of one
  device each. Here a daemon that already serves Home Assistant's
  controller API and declared bridge nodes can be the device that leaves
  the box — commissioned over Bluetooth, onto the Wi-Fi it is given — with
  two flags and no build of its own.
- **Better than before.** Until 0.10.0 the daemon's node needed an IP
  network at its first start; a host without one (a Raspberry Pi in a new
  home) had to be put on the network by hand first. Now the commissioner
  does it, the way every Matter device is set up, and the node falls back
  to the radio when its last fabric goes.
- **The right cut.** The radio and the Wi-Fi are host ports of the first
  node (go-fabric's `node.Network.BLE`, `node.Network.WiFi`), opened by the
  daemon, which owns the host: the Matter behaviour (when to advertise,
  PASE, NetworkCommissioning, leaving the radio) stays in go-fabric, the
  server only composes. The registry's nodes stay IP bridges (one adapter
  advertises one node). The add-on is unchanged: its host has a network
  already, and it keeps no system-bus access. The proven-address retention
  belongs in go-fabric's controller facade first, so it waits for it rather
  than reaching below the facade.

## Decisions

- One `nodeRadio` for the daemon's life, reused by every run of the first
  node (above), rather than a port per run.
- `nodeRadio.apply` checks the node's key itself, so `bridgeConfig` cannot
  give the radio to a registry node even when handed one.
- `TestRunNodeRadio` runs `Run` with the controller off: the controller's
  central is a separate seam with its own tests.

## Work that needs go-fabric (ready to file)

**controller: let the host set the peer set's timing (`controller.Config`)**

- *Why.* go-fabric-server's `--controller-proven-address-retention`
  (brief S12, decision 6) needs to set
  `client/peer.Timing.ProvenAddressRetention` (issue 507, W15) on the
  controller's peer set. The server reaches go-fabric through the facade
  only; the facade has the type (`controller/client.Timing`,
  `controller/client/surface.go:124-126`) but no field that takes it.
- *Sources (v0.22.2).* `client/peer/timing.go:49-66`
  (`ProvenAddressRetention`, default 10 min, negative retains nothing);
  `client/peer/set.go:46-47,141-144` (`Context.Timing`, merged field-wise
  over `DefaultTiming`); `controller/controller.go:92-228` (`Config`, no
  timing field), `:366-374` (`peer.Context` built without `Timing`).
  matter.js has no such parameter (the field's own doc), so no parity case.
- *Shape.* `controller.Config.PeerTiming *client.Timing` (nil: the
  defaults; a zero field: its default), passed as `peer.Context.Timing`.
- *Acceptance.* A controller built with `PeerTiming{ProvenAddressRetention: -1}`
  retains nothing; one with a positive value retains for it; nil keeps
  10 min (`Set.Timing()` reflects each); a facade test; the CHANGELOG line.
- *Stays here.* The flag, its validation, docs and the test that the value
  reaches `controller.Config`.
- *Open.* Whether the other `Timing` fields should be host-settable too
  (the server needs only the retention).
